NSS · plano técnico · decisão arquitetural

Centralizar o banco sem centralizar o dado bruto.

Este documento descreve como transformar o NSS-database na fonte oficial do schema, migrations, permissões e contratos do PostgreSQL, preservando a autonomia do Java, da pipeline e do Deployment.

Status: planejamentoAmbiente: pré-produçãoObjetivo: uma fonte de verdade

A decisão recomendada

Centralizar o ciclo de vida do schema

É correto porque Java e Pipeline compartilham o mesmo PostgreSQL e o schema analítico é um contrato entre componentes. A aplicação deve consumir um banco previamente preparado; não deve decidir sozinha, durante o boot, qual estado estrutural o banco precisa ter.

O que será centralizado: migrations, seeds determinísticos, permissões esperadas, índices, contratos, diagramas, testes e consultas de referência.

O que continuará fora do Git: volumes PostgreSQL, dados reais, Parquets completos, tokens e credenciais.

Migrations distribuídas

O Java mantém o schema operacional e a Pipeline mantém o schema analítico. O Deployment orquestra ambos, mas a definição do banco está espalhada.

Risco de ordem

Uma alteração em analytics pode ser publicada sem que o Java tenha validado a consulta correspondente, ou vice-versa.

Diagnóstico difícil

Fica menos evidente qual repositório representa o estado oficial do banco e qual versão foi aplicada.

Deployment ── aplica migrations ──► PostgreSQL
                                      ├── public       ◄── Java
                                      └── analytics    ◄── Pipeline

O Deployment passa a executar o banco antes de subir Java, Pipeline sob demanda, Frontend e observabilidade. Java e Pipeline recebem usuários com privilégios limitados e não fazem DDL em runtime.

Plano de execução

1

Inventário e congelamento

Catalogar Flyway, Alembic, DDL, índices, seeds e permissões atuais. Congelar mudanças estruturais durante a migração para evitar duas fontes divergentes.

Saída: matriz de objetos e versão de referência.

2

Definição do estado inicial

Consolidar o estado atual em uma migration inicial única, equivalente ao banco aprovado. Validar tabelas, constraints, índices, roles e grants em PostgreSQL limpo.

Saída: 0001_initial_schema reproduzível.

3

Portabilidade dos consumidores

Remover a execução automática duplicada do Flyway no Java e do Alembic na Pipeline. Os dois componentes passam a falhar com mensagem clara quando o schema esperado não existe.

Saída: nenhum serviço aplica DDL por conta própria.

4

Orquestração no Deployment

Criar um serviço/job de migration com imagem e versão fixas. A ordem será: banco → permissões → migration central → Java/Pipeline → frontend/Caddy.

Saída: runbook idempotente e observável.

5

CI e testes de contrato

Subir PostgreSQL limpo no CI, aplicar todas as migrations, executar testes de schema e validar as queries Java e o loader da Pipeline contra o mesmo contrato.

Saída: PR bloqueado quando migration, query ou permissão quebrar.

6

Cutover e validação

Aplicar em ambiente vazio, carregar uma doença de referência, comparar contagens Bronze/Silver/Gold/PostgreSQL, validar login, mapa, dashboards e consultas de município/UF/região.

Saída: checklist de aceite assinado e banco reproduzível.

Riscos e controles

Duplicação temporária de migrations

Será controlada com uma janela de congelamento e uma única migration consolidada. O CI verificará que Java/Pipeline não contêm uma segunda fonte ativa.

Diferença entre banco existente e migration inicial

Antes do cutover será feito inventário e dump de estrutura. O baseline será comparado por catálogo PostgreSQL, não apenas por arquivos.

Permissões insuficientes

O job de migration usará usuário migrador; Java terá apenas leitura/escrita operacional autorizada e Pipeline terá os grants mínimos para analytics.

Rollback

Migrations destrutivas não terão downgrade automático. O rollback operacional será feito por imagem anterior e restauração de backup aprovado. Em pré-produção, será possível recriar o volume.

Critérios de aceite

  • Um PostgreSQL vazio sobe com o comando documentado e chega ao estado oficial sem intervenção manual.
  • Java, Pipeline e Deployment usam a mesma versão de schema registrada.
  • O CI aplica migrations em banco limpo e testa upgrade a partir de uma versão anterior.
  • As roles não conseguem executar DDL fora do usuário migrador.
  • Uma carga de DENG de referência reconcilia Bronze, Silver, Gold e PostgreSQL.
  • As consultas de região, UF, município, distrito e bairro continuam retornando os mesmos resultados funcionais.
  • O runbook informa etapa, duração, logs e causa de falha.

Resultado esperado

Ao final, o banco deixa de ser um efeito colateral de dois serviços e passa a ser um produto versionado, testável e reproduzível. O NSS-database será a fonte oficial do estado estrutural; o PostgreSQL continuará sendo a fonte dos dados carregados em execução.
